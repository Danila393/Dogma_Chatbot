# Архитектурные решения (ADR)

Формат: контекст → решение → последствия. Неоднозначности задания решены здесь.

## ADR-001. SQLite вместо PostgreSQL
**Контекст.** ~15 тыс. лотов, один писатель (синхронизация), чтение из API, тестовое задание.
**Решение.** SQLite (WAL, `busy_timeout`) через SQLAlchemy 2.x async + aiosqlite, файл в Docker volume.
**Последствия.** Ноль инфраструктуры, запуск одной командой. Горизонтальное масштабирование
и конкурентная запись — не цель; переход на PostgreSQL сводится к смене `DATABASE_URL` и
диалекта UPSERT в одном методе репозитория.

## ADR-002. FastAPI
**Решение.** FastAPI + Uvicorn: Pydantic v2 из коробки, OpenAPI/Swagger без кода, async,
DI через `Depends`. Swagger UI закрывает требование «простого AI-интерфейса».

## ADR-003. Парсер отделён от поиска
**Решение.** Сбор данных — отдельная CLI-команда и отдельный процесс; поиск работает
только по локальной БД.
**Последствия.** Ответ пользователю не зависит от доступности сайта и не создаёт на него
нагрузку; синхронизацию можно повесить на cron. Парсер не знает о БД — его вывод
(нормализованные модели) сохраняет `SyncService`.

## ADR-004. Tool Calling (OpenAI-совместимый протокол)
**Решение.** Модель обязана вызвать один из двух инструментов: `search_apartments`
(аргументы = JSON Schema, сгенерированная из Pydantic-модели фильтров) или
`reply_without_search` (оффтоп / уточнение / противоречие). Аргументы валидируются
Pydantic; при ошибке схемы — один повтор с текстом ошибки.
Провайдер — любой OpenAI-совместимый endpoint (`LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`):
OpenAI, OpenRouter, DeepSeek, YandexGPT/GigaChat через совместимые шлюзы, локальный
Ollama/vLLM. Бизнес-логика зависит только от протокола `LLMProvider`.
**Почему не свободный текст.** Структура проверяется кодом; LLM не может «сказать»
пользователю цену или ссылку — сообщение формирует backend по шаблону.

## ADR-005. Без RAG и векторных БД
**Решение.** Запросы — это фильтры по числовым полям и короткому справочнику ЖК
(14 названий). Справочник ЖК передаётся в промпт целиком, квартиры — никогда.
Семантический поиск по эмбеддингам дал бы неточные границы («до 7 млн») и галлюцинации.

## ADR-006. Без LangChain/LangGraph
**Решение.** Граф агента линеен: «текст → один вызов инструмента → поиск». ~150 строк
собственного кода прозрачнее и проще тестировать, чем фреймворк с собственными
абстракциями и зависимостями.

## ADR-007. Детерминированное ранжирование
**Решение.** Сортировка в SQL: `price_asc` (цена ↑, площадь ↓, id ↑) по умолчанию,
`area_desc` (площадь ↓, цена ↑, id ↑), `price_per_sqm_asc` (цена м² ↑, цена ↑, id ↑).
Объяснения генерирует Python из тех же чисел, что возвращаются в JSON.
**Последствия.** Воспроизводимость, тестируемость, отсутствие расхождений текста и данных.
Пользовательские ограничения никогда не ослабляются автоматически.

## ADR-008. Источник данных — публичный JSON API сайта
**Контекст.** Приоритеты задания: JSON API → встроенный JSON → HTML → Playwright.
**Решение.** `POST service.dogma.ru/api/layouts-filter/v4/objects/filter` + `config/all`
(см. `SOURCE_RESEARCH.md`). Тот же API использует фронтенд сайта; авторизации нет.
**Последствия.** Нет хрупкого HTML-парсинга и браузера в контейнере. Риск — изменение
недокументированного API; он локализован в `app/parser/schemas.py` и `client.py`,
формат проверяется Pydantic, а ошибки формата не портят БД.

## ADR-009. Конкурентность: asyncio + Semaphore
**Решение.** Один `httpx.AsyncClient`, `asyncio.Semaphore(PARSER_CONCURRENCY=3)` и
минимальный интервал между стартами запросов. Города последовательно, страницы —
параллельно с ограничением.
**Уточнение по итогам реального запуска.** Источник отвечает `429`, если сразу после полного
сбора начать второй. Поэтому 429 обрабатывается отдельно от прочих ошибок: общий для всех
воркеров `RateLimiter` ставит паузу (`Retry-After` или 5→10→20→40→60 с) и удваивает интервал
между запросами (до 5 с); после 20 успешных запросов подряд интервал снова уменьшается.
**Почему не потоки/процессы/Celery.** Нагрузка — I/O, ~150 запросов на полный сбор;
asyncio даёт контроль без накладных расходов и внешних брокеров.

## ADR-010. Схема без Alembic
**Решение.** `metadata.create_all` при старте API и CLI.
**Последствия.** Проще для тестового задания; при развитии проекта следующим шагом
должен стать Alembic (отмечено в README).

## ADR-011. Площадь как целое число сотых долей м²
**Решение.** `TypeDecorator` хранит `Decimal('32.30')` как `3230`. См. ARCHITECTURE §4.1.

## ADR-012. Снятие лотов только после подтверждённо полного сбора города
**Решение.** Лот получает `unavailable`, только если сбор его города прошёл без ошибок и
лимитов, и число увиденных id ≥ `count` из API. Снятие ограничено городом, и используются
`id`, увиденные в ответе (включая невалидные объекты), — частичная или аварийная
синхронизация не может «снять» реальные квартиры.

## ADR-013. Разрешение названия ЖК — в backend
**Решение.** LLM передаёт название ЖК как сказал пользователь. `ComplexResolver`
нормализует строку (регистр, `ё/е`, кавычки, префиксы «ЖК», «МКР», «микрорайон») и ищет
среди названий из БД: точное совпадение → используем; единственный близкий кандидат
(подстрока или `difflib` ≥ 0.8) → используем и сообщаем, как интерпретировали; несколько
или ни одного → просим уточнить и перечисляем варианты.
**Пример.** «Самолет» → «МКР Самолёт»; «Самолёт 7» → «САМОЛЁТ 7» — это разные ЖК.

## ADR-014. Сообщение пользователю формирует backend
**Решение.** Текст ответа (`message`) и объяснения — шаблоны с подстановкой фактических
данных. Текст, который модель пишет вне инструментов, пользователю не передаётся;
для `clarification` передаётся только вопрос модели (≤ 300 символов), без данных о квартирах.

## ADR-015. Telegram-бот как HTTP-клиент API
**Контекст.** В исходном ТЗ интерфейс — «чат, Telegram-бот или API»; базой выбран API,
бот добавлен по желанию автора как небольшой дополнительный слой.
**Решение.** Бот (aiogram 3, long polling) — отдельный процесс/сервис Compose
(`profile: bot`), который вызывает `POST /api/v1/chat` и только форматирует ответ.
**Последствия.** Нет дублирования бизнес-логики и второго подключения к БД; бот можно
выключить, не затрагивая API. `docker compose up` без токена бота работает как раньше.

## ADR-016. Значения по умолчанию
- Выдача: 5 квартир по умолчанию, максимум 10.
- Длина сообщения в чат: 1–1000 символов.
- В выдаче только `status = available`.
- Валюта — рубли; «млн», «лям», «тыс.», «200к» переводит Python (ADR-017), границы включительные
  («до 7 млн» → `max_price = 7 000 000`).
- Город — необязательный фильтр по точному (нормализованному) названию.
- Без настроенной LLM `POST /api/v1/chat` возвращает `503 llm_not_configured` (ADR-018).

## ADR-017. Явные числа из текста разбирает Python, а не LLM
**Контекст.** Реальная проверка с локальной `qwen2.5:7b` (Ollama) показала типичные ошибки
малой модели: «студию» → `rooms=1`, «9 лямов» → `90 000 000`, «от 10 до 5 млн» →
`max_price=50 000 000` вместо противоречия. Backend при этом корректно искал по неверным
фильтрам — пользователь получал реальные, но не те квартиры.
**Решение.** `app/agent/hints.py` детерминированно извлекает из исходного текста явно
названные ограничения: тип квартиры (студия/однушка/…/«3-х комнатная»), цены с единицами
(«млн», «миллионов», «лямов», «тыс», «200к», «₽», числа словами, «12,5»), площади («м²», «квадратов»,
«метров») и диапазоны «от X до Y». Эти значения заменяют аргументы модели; расхождения
пишутся в лог. Явно перевёрнутый диапазон сразу даёт `contradiction` без вызова LLM.
Парсер ничего не добавляет «от себя»: без единиц измерения малые числа («от 30»), этажи и
названия ЖК остаются за моделью; если в тексте два разных значения одного поля, оно не
переопределяется.
Сумма, относящаяся к квадратному метру («метр не дороже 200 тысяч», «до 700 тыс за м²»,
«цена метра до 180 тыс»), распознаётся по соседним словам и уходит в отдельный фильтр
`max_price_per_sqm` / `min_price_per_sqm`, а не в бюджет; если модель поставила ту же сумму
в `max_price`, это значение отбрасывается.
**Последствия.** Корректность чисел не зависит от размера модели — требование «все числовые
расчёты выполняются Python-кодом» соблюдено и на входе. LLM отвечает за то, что плохо
формализуется: названия ЖК, город, сортировку, оффтоп и уточнения.

## ADR-018. Без LLM чат отвечает ошибкой конфигурации, а не упрощённым режимом
**Контекст.** Чат без модели можно было бы обслуживать эвристикой: `extract_hints` уже
разбирает цену, площадь, комнаты и цену за м².
**Решение.** Без настроенной модели `POST /api/v1/chat` возвращает `503 llm_not_configured`
с подсказкой, какие переменные задать. Упрощённого режима нет.
**Почему.** Эвристика понимает только явные числа и типы квартир. Названия ЖК в свободной
форме («в Самолёте», «Юкки»), город, сортировку («самая просторная»), вопросы не по теме и
противоречия, выраженные словами, без модели не разобрать — такой чат молча возвращал бы
квартиры по неполному набору условий. Явная ошибка честнее: сразу видно, что AI-часть
выключена. Сценарии без LLM закрывают `POST /api/v1/apartments/search` и
`GET /api/v1/complexes`; для чата достаточно любой OpenAI-совместимой модели, проще всего
локальной Ollama (README, «Быстрый старт»).
**Последствия.** Чтобы увидеть агента, нужна модель — ключ облачного провайдера или Ollama
(`qwen2.5:7b`, ~4,7 ГБ, бесплатно и без регистрации).
